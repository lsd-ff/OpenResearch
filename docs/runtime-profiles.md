# 命名运行时与目标 Python 验证

2026-10-20：已交付受配置约束的沙箱运行时基础、科研/框架计划的 CPU 版本选择与初始准备恢复，并继续补齐普通代码和执行阶段的 CPU 版本恢复。GPU/full 模式、资源准入与补丁版本探测仍待补齐，不能把本页验收当作完整训练调度已经完成。

## 配置契约

`OPENRESEARCH_RUNTIME_PROFILES` 默认为空对象，保留已有默认镜像和旧计划行为。管理员可在 API、Worker、Sandbox 使用相同的 JSON 注册命名配置，例如：

```json
{
  "cpu11": {"image": "python:3.11-slim-bookworm", "python": "3.11", "memory_mb": 256},
  "cpu13": {"image": "python:3.13-slim-bookworm", "python": "3.13", "memory_mb": 256},
  "cuda12": {"image": "python:3.12-slim-bookworm", "python": "3.12", "gpu": true, "memory_mb": 512}
}
```

最多 16 项，支持目标 CPython 3.11、3.12、3.13。每项限制镜像引用、CPU、内存及是否请求 GPU。仅管理员配置可以指定镜像，调用方只能引用已有名称。当前 GPU 请求透传可见设备，不提供显存配额或跨 Worker 的 GPU 并发准入；不要将其作为多任务 GPU 调度能力。

原生 Docker 保留非 root、只读根目录、capability 清除、默认无网络及工作区/进程限制。命名 GPU 配置使用实际 Docker DeviceRequest。HTTP 服务确认名称与配置 SHA-256；服务端注册不同、旧服务忽略名称时，客户端清理已创建容器并失败，不能静默退回默认环境。`GET /api/v1/runtime-profiles` 遵循沙箱服务的认证。OpenSandbox 可使用命名 CPU 配置；当前适配器不能保证 GPU 分配，明确拒绝 GPU 配置。

## 环境绑定

解析器、wheel ABI 选择、Requires-Python、依赖 marker 和容器安装器使用同一目标版本。环境锁的旧默认 JSON 格式及摘要保持兼容；实际 Python 次版本与注册信息不符时安装失败。支持平台为 Linux x86_64、glibc 不低于 2.36，安装器再次核对实际版本和完整依赖闭包。

解析阶段目前按目标 `X.Y.0` 计算完整版本条件；实际安装器会按真实补丁版本复核，部分只适用于较新补丁版本的包可能被保守拒绝。解析前的实际补丁版本探测仍待接入。

标准库识别不再取决于宿主机 Python。`sources/stdlib.json` 来自三个真实目标容器，保存实际 Python、平台、glibc、镜像 ID 和模块名称；移除的标准库不会被悄悄当作同名 PyPI 包补装。可用以下命令刷新元数据，实验依赖仍只在容器安装：

```powershell
uv run --locked python scripts/capture_stdlib.py
```

## 科研计划与初始版本恢复

科研计划可从用户明确的 Python 版本或范围中选择管理员注册的 CPU 配置，例如「用Python3.13运行」或「用 Python >=3.13,<3.14 运行」。选定名称和配置摘要保存在 `ResearchSpec.runtime`，依赖解析、wheel、预检、正式运行、消融及后续依赖修复使用同一目标。不同版本的并行分支各用独立解析器，不能修改共享实例的版本。默认配置为空时保持 Python 3.12；没有注册的目标会明确失败。

首次解析或锁定实际失败后，受 `runtime.select` 权限及原修复次数限制，可根据当前请求版本的真实 PyPI Requires-Python 证据选择兼容 CPU 配置。保留原包、用户版本、源码与验收条件，重新解析完整依赖闭包。最新发行版若不在当前请求范围内，不能用来证明应切换运行时。没有权限、禁用修复、明确指定 Python/运行时、禁止切换或没有兼容配置时不会自动换版本。框架准备接入相同恢复器，实际主包/API 来源仍按采用版本绑定。

每轮准备及决策记录目标运行时，最终报告保留实际解释器、完整锁、镜像 ID 与错误。配置变动会使旧绑定失效；预检摘要包含运行时，不能把旧运行时的通过记录用于另一个配置。旧规范未指定 runtime 时不新增空序列化字段，保持既有预检摘要兼容；旧任务不会自动获得新权限。GPU 研究配置在资源准入接入前明确拒绝。

## 普通代码与执行阶段恢复

普通代码计划同样采用管理员注册的 CPU 配置，报告保存每次实际环境、目标及原代码摘要。若宿主解释器不能判断更新版本的语法，准备阶段只检查体积并明确标记 `syntax_pending` / `deferred_to_sandbox`，原代码交给实际目标容器执行，不能误报宿主已完成语法验收。实际 Python 3.13 容器已通过包含类型参数默认值的原代码，输出值 61，原断言和源码摘要不变。

执行中补充依赖时，真实解析或锁定错误可触发兼容 CPU 选择；仍须保留原包与用户约束、验证公开元数据、完整 wheel 闭包及哈希。补依赖占一次修复，另一次运行时切换也消耗原节点预算；预算仅余一次时不得将两项操作包装成一次修复。没有 `runtime.select` 的旧任务、用户固定配置、禁止切换或排除目标的版本范围都不能换运行时。用户原文中的中文与库名紧贴时仍识别版本约束；代码块里的字符串不能变成依赖指令。

科研运行中的目标随实际恢复环境进入预检回执和最终报告。预检阶段换环境后，正式运行必须采用该目标；正式运行换环境后先在独立容器重新运行最多 8 条样本，未通过时不执行全量。源码、依赖和运行时恢复共用原节点最多两次修复；不得多调用一次代码修复来绕过已花完的预算。失败的重新预检把实际 stderr 保留到错误摘要，完整原始错误仍在对应回执。
