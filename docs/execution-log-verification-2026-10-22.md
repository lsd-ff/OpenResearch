## 两处实测缺陷

前端恢复计划时只恢复节点结果，日志缓存初始化为空；聊天自动排队也没有连接计划事件流。现在进入计划即以当前身份读取并绑定 Cookie，回放已有 SSE 事件，再继续订阅后续事件。服务端原有序号、分页和重连游标继续生效，前端按序号去重。切换身份/会话时关闭旧连接并隔离缓存；已完成节点直接恢复完整报告，不能被空日志缓存或事件短摘要覆盖。日志标签在尚无结果时也可查看。

历史事件可能包含失败后重试；客户端不能看到旧终态就提前关闭回放，也不能重复追加旧完成消息。现在读完终态流后关闭连接，异常中断仍由 EventSource 携带 Last-Event-ID 恢复；显式重试使用当前游标。

首个真实任务 `5de0a3cb932f41a9bf6416f3a75b64b6` 的程序与 3 条断言均成功，但 20 条日志集中写入，未满足实时展示要求。继续定位发现 HTTP 传输解析器使用 `aiter_bytes(chunk_size=65536)`，不足 64 KiB 的日志会等到 EOF 才向上交付。现改为按实际到达的数据块解析，继续保留累计字节限制、跨块行拼接、UTF-8、NDJSON/SSE 和最终回执校验。原任务记录保留，没有用一次成功退出代替实时性验证。
